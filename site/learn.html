How this thing works

Blacksite is built out of a handful of ideas that aren't obvious until someone spells them out. This page explains each one twice: what the concept is in general, and how Blacksite actually implements it. Every section links to the source or a deeper design document, because the point of a source-available tool is that you can go check.

The agent loop

A language model on its own does one thing: given text, it produces more text. It cannot open a file or run a command. An agent loop is the machinery that turns that into something that can act.

The shape is simple, and almost everything else is a consequence of it:

  1. Send the model the conversation, plus a list of tools it may call.
  2. The model replies with either prose (it's done) or a request to call a tool.
  3. Execute the tool. Append the result to the conversation.
  4. Go back to step 1.

The model never touches your machine. It emits a structured request; the harness decides whether and how to honour it. That boundary is where all the safety and all the engineering lives — approval gates, sandboxing, output limits, and loop detection are all decisions made in step 3, not by the model.

This is also why "the AI deleted my files" is really a harness bug. The harness chose to run the command. Blacksite routes every file edit through an approval gate before it touches disk.

Tool calling and schemas

A tool is a function the model can ask to call, described by a JSON Schema: a name, a description, and typed parameters. The model has never seen your tool before; the schema and its description are the entire interface. Tool design is API design where the consumer reads the docs exactly once and cannot ask questions.

Blacksite advertises roughly 140 tools grouped into 19 families — file operations, search, shell, git, LSP queries, map queries, planning, browser automation, and more. Schemas live in one declarative module so the whole surface can be read in one sitting.

The subtlety is that providers disagree about schemas. Anthropic supports a stricter dialect than the baseline; OpenAI's structured-output mode has its own rules. So the same tool definitions get converted per provider at request time rather than being authored several times.

Provider neutrality

Every model vendor invented a different wire format. Anthropic streams one event shape, OpenAI streams another, OpenAI's newer Responses API a third, and AWS Bedrock offers two more. Message roles, tool-call encoding, streaming deltas, stop reasons, and reasoning/thinking blocks all differ.

The methodology here is an old one: normalize at the edges, keep the core single-shaped. Blacksite has five separate streaming implementations that all emit one internal event type. The agent loop has no idea which provider it's talking to. Adding a provider means writing one adapter, not touching the loop.

The payoff shows up in features nobody plans for. Because the core is provider-neutral, you can switch models mid-project, or run a subagent on a cheap model while the main loop uses an expensive one, without any of that logic knowing about vendors.

Context windows and compaction

Models have a fixed context window — the maximum number of tokens they can consider at once. Every message, every tool result, every file you attach consumes it. A long agent session will exhaust any window, because tool results accumulate faster than conversation does.

Compaction is the answer: when the conversation approaches the limit, summarize the older portion and replace it with the summary. The agent keeps working; it just remembers the distant past in less detail, the way you'd remember a meeting from three hours ago.

Doing this well is harder than it sounds. Compaction itself costs a model call, so a naive implementation can spiral: compact, immediately overflow again, compact again. Blacksite runs compaction in the background where it can, blocks only when it must, and has a circuit breaker so a pathological session degrades instead of burning tokens in a loop.

Prompt caching

Providers will cache a prefix of your request and charge far less to re-read it. Since an agent loop resends the whole conversation on every single iteration, this is not a micro- optimization — it is the difference between a workable tool and an unaffordable one.

The rule that makes it work: caches key on an exact prefix. Anything that changes invalidates everything after it. So stable content — system prompt, tool schemas, early conversation — must come first, and volatile content must come last. Put a timestamp near the top of your prompt and you have silently disabled caching for the entire session.

Blacksite places cache breakpoints just before the volatile tail on every provider path that supports it.

Building a map of a codebase

To show you a codebase as a graph, something has to decide what the nodes and edges are. Nodes are easy: files. Edges are the interesting problem, and it's a static analysis question — determining structure by reading code rather than running it.

The pipeline runs in two stages, and separating them is the whole trick:

  1. Scan each file for import statements. This is per-language pattern matching — fast, tolerant of broken syntax, and cheap enough to run over a very large repository.
  2. Resolve each import string to an actual file. This is where the real difficulty lives, and it is unavoidably per-ecosystem: TypeScript path aliases from tsconfig.json, Go module paths, Java and C# namespaces, Python packages and re-exports, PHP autoload rules.

A full parser per language would be more precise and vastly more expensive. Scanning plus resolution gets most of the accuracy for a small fraction of the cost, and degrades gracefully when it meets code it doesn't understand.

On top of that sits a service lens: detecting that one service calls another's HTTP API, publishes an event it consumes, or writes a table it reads. The hard part is precision — a naive matcher pairs any route string with any similar-looking URL and produces a hairball. Blacksite requires the client side to be verified before drawing the edge, so a line means a call that plausibly exists rather than two strings that rhyme.

Graph layout, and knowing when to change algorithm

Once you have a graph you must position it. The standard approach is force-directed layout: treat edges as springs and nodes as mutually repelling particles, then simulate until it settles. It produces genuinely good results — related things cluster because the physics pulls them together.

It is also roughly O(n²) per tick. Beautiful at 2,000 nodes, unusable at 60,000.

Rather than accept a slow map on large repositories or a mediocre one everywhere, Blacksite switches algorithms at a threshold of 6,000 nodes, falling back to a linear-time phyllotaxis-style packing. This is a broadly useful methodology: an algorithm that is optimal in the common case and one that degrades gracefully in the extreme case are not competitors. Pick a threshold and ship both.

Using the editor's own intelligence

The Language Server Protocol is how editors get real semantic understanding. A language server for each language runs alongside the editor and answers structured questions: where is this symbol defined, what are its references, what type is this, what's wrong with this file.

This matters enormously for an agent. Ask a model to rename a symbol and it will pattern-match on text and miss cases. Ask a language server and you get the same answer the editor's own rename command would — because it is that command.

So Blacksite exposes LSP queries as agent tools. Symbols, navigation, type hierarchies, diagnostics, rename, and code actions are the toolchain you already trust, not a reimplementation. And after every edit, diagnostics are collected and fed straight back, so the agent finds out it broke the build before you do.

Extension host and webview processes

A VS Code extension runs in the extension host, a Node.js process with filesystem and network access but no DOM. Any custom interface runs in a webview: a sandboxed browser context with a DOM but no filesystem, no require, and a strict Content Security Policy.

The two communicate only by passing serializable messages. That constraint shapes everything. State that both sides need must be deliberately synchronized; anything expensive must be computed host-side and sent over; and payload size becomes a real performance concern, since every message is serialized and deserialized.

Blacksite runs six separate webview bundles — chat, plans, base context, data, map, and notes — each an independent application talking to the same host. The map is the demanding one: it renders with WebGL through pixi.js, and the graph payload it consumes can be large enough that how you send it matters as much as how you draw it.

Reliability engineering for long-running agents

A single model call failing is a nuisance. An agent loop running for an hour across hundreds of calls will meet every transient failure mode there is: rate limits, timeouts, overloaded servers, streams that stop producing without closing, malformed tool calls.

The patterns that keep it alive are all conventional, and all necessary:

  • Retry with exponential backoff on transient errors, with jitter so retries don't synchronize.
  • Idle timeouts on streams, because a stream that stalls without erroring will otherwise hang forever.
  • Circuit breakers, so a failing subsystem stops being retried rather than consuming the whole budget.
  • Bounded queues and output caps, so one enormous tool result can't exhaust memory or context.
  • Checkpointing, so a crashed session can resume rather than restart.

Blacksite keeps this in one shared module rather than scattering try/catch through the provider layer. It's the least glamorous code in the project and probably the highest-value.
